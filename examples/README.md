# USBHawk demo kit

Try every USBHawk module in a few minutes, then on real evidence. Each command below is run by the test suite
(`tests/examples_demo/`), so what you see here is what you get.

| Module | Command | Demo data | Question it answers |
|---|---|---|---|
| #2 sessions | `usbhawk sessions`, `usbhawk devices` | public sample hives and logs (fetched) | Which USB sessions look like data exfiltration, and why? |
| #3 tamper | `usbhawk tamper` | public sample hives and logs (fetched) | Did someone wipe the USB evidence, or did Windows clean it up? |
| #4 detections | `usbhawk detections ...` | `examples/detections/` (fictional, included) | Would my SIEM catch it live? |
| #1 graph | `usbhawk graph` | `examples/fleet/` (fictional, included) | Where else has this stick been, and who else used it? |

Run the commands from the repository root. With the standalone build, use `usbhawk.exe` (or `.\usbhawk.exe`) in place of
`usbhawk`; with only Python, `python -m usbhawk` works too.

## What is in this folder

```
examples/
  fleet/                         module #1 input: four fictional hosts, as `usbhawk sessions/tamper --out` writes them
    NW-FIN-WS042/                  finance PC: a Kingston stick with a high-risk session (61 writes, score 85)
    NW-HR-WS007/                   HR PC: the same Kingston later, plus a SanDisk wiped elsewhere
    NW-ENG-LT113/                  engineering laptop: the Kingston again, and a brand-new stick
    NW-OPS-WS019/                  ops PC: the SanDisk was wiped here with USBOblivion (tamper.jsonl)
  detections/
    insider_timeline.jsonl       module #4 input: 72 events of a Friday-evening insider, one JSON object per line
```

Everything here is **fictional** (hosts `NW-*`, users `NW\j.doe`, `NW\a.smith`, `NW\k.lee`, `NW\m.ortiz`, invented
serials). It is generated by `python scripts/make_examples.py` from the same builders the tests use, and a test fails if
these files and the generator ever disagree.

Why fictional data for #1 and #4 but real data for #2 and #3? Modules #1 and #4 read text (JSONL), which can be written
by hand without losing realism. Modules #2 and #3 parse binary registry hives and `.evtx` logs, and a made-up hive
would only prove the tool reads made-up hives. So those demos use real public evidence, fetched on demand and never
committed (see [Real evidence](#real-evidence)).

## Module #4 detections: replay an insider timeline through the rules

The story: `j.doe` plugs in a Kingston stick at 21:14 UTC on a Friday, copies 64 board-pack documents, writes a 7z
archive, reformats the stick, then runs USBOblivion, which deletes the stick's registry keys and clears the Security log.

```powershell
usbhawk detections list
usbhawk detections test
usbhawk detections run --events examples\detections\insider_timeline.jsonl
usbhawk detections run --events examples\detections\insider_timeline.jsonl --out out\detections
usbhawk detections build --out out\rules
```

Expected output of `detections run` (every hypothesis H1-H8 fires, in order; trimmed to one line per alert):

**Your own logs:** `usbhawk detections run --evtx C:\Windows\System32\winevt\Logs --removable-drives F:` replays real
Sysmon, Security and System logs (run as administrator). The neutral event format of `insider_timeline.jsonl` is the
same one the rules are written in, so you can also convert any SIEM export to it and replay that.

## Module #1 graph: follow a stick across a fleet

`usbhawk graph` reads the per-host output folders of `usbhawk sessions --out` and `usbhawk tamper --out` (never raw
evidence) and links the same stick across hosts by serial, then volume serial, then name and capacity.

```powershell
usbhawk graph --runs examples\fleet
usbhawk graph --runs examples\fleet --out out\fleet
usbhawk graph --runs examples\fleet device 60A44C41
usbhawk graph --runs examples\fleet user a.smith
```

Expected findings (all six fleet hunts fire):

```

| high     | exfil_device_spread    | Kingston DataTraveler 3.0 (60A44C413D5FF380E95A0B7D) | 3   |  score 85 on NW-FIN-WS042, also on NW-ENG-LT113, NW-HR-WS007
```

## Modules #2 and #3: sessions, devices and tamper on real public evidence

Fetch the small public samples first (about 30 MB; MIT-licensed hives from the regipy project and a Partition/Diagnostic
log from Partition-4DiagnosticParser). They go to `tests\data`, which is never committed:

```powershell
python scripts\fetch_test_samples.py
```

```powershell
usbhawk sessions --triage tests\data --tz America/New_York
usbhawk sessions --triage tests\data --tz America/New_York --out out\sample-host
usbhawk devices --triage tests\data
usbhawk tamper --triage tests\data
```

Expected output of `sessions` (trimmed): a Windows 7 host, and a Patriot stick reformatted between sessions.

```

| 40 medium | 2020-11-29 09:47:03 | 3m  | usbstor | Patriot Memory  | 0701935D84A40B14 | DAFBDA6E, 8C09DE0F… | off_hours; reformat_or_repartition
```

`devices` prints one JSON line per device (the FOR500 11-step profile), for example the HP v100w stick with volume

different machines, and USBHawk says so instead of raising false tamper alerts.

## Real evidence

`scripts/fetch_demo_datasets.py` downloads public forensic datasets into a folder of your choice (default
`~\usbhawk-datasets`, outside the repository), verifies their published hashes and prepares a triage folder. Nothing is
bundled with USBHawk; each dataset keeps its own licence and terms.

| Dataset | Size | What it shows | Source |
|---|---|---|---|
| `evtx-attack` | 1.2 MB | real Security 1102 and System 104 log-clearing records (module #4, H7) | EVTX-ATTACK-SAMPLES by Samir Bousseaden (GPL-3.0) |
| `nist-leakage` | 5.1 GB download, 21 GB unpacked | a scripted insider data-leakage case on Windows 7 with two USB sticks and a written answer key (modules #2, #3, #1) | NIST CFReDS Data Leakage Case (2015) |

```powershell
python scripts\fetch_demo_datasets.py evtx-attack
python scripts\fetch_demo_datasets.py nist-leakage
```

The NIST download needs 7-Zip (`7z` on the PATH or in `C:\Program Files\7-Zip`) to unpack the image and copy out the
registry hives and event logs. What USBHawk finds on it, compared with NIST's answer key, is in
[docs/TESTING.md](../docs/TESTING.md).

Other public datasets worth knowing: the Mendeley "Windows Registry Data Sets" (Kwon, CC BY 4.0,
doi:10.17632/ghkms3cgbg.1) are `.reg` text exports, which USBHawk does not read yet (see
[ideas/](../ideas/README.md)); Digital Corpora's M57-Patents scenario has several hosts for a fleet test.
